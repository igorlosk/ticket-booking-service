📚 Теория

JPA / Hibernate / Spring Data JPA — иерархия

Spring Data JPA ← ты пишешь код здесь (JpaRepository) ↓ JPA (интерфейсы) ← спецификация (Jakarta Persistence) ↓ Hibernate ← реализация (генерит SQL) ↓ PostgreSQL ← БД
  • JPA — спецификация (набор интерфейсов и аннотаций). Сама по себе ничего не делает
  • Hibernate — реализация JPA. Генерит SQL, управляет транзакциями
  • Spring Data JPA — надстройка. Даёт JpaRepository с готовыми методами

Ключевые аннотации JPA

АннотацияЧто делает
@EntityКласс → таблица БД
@Table(name = "events")Явное имя таблицы
@IdПервичный ключ
@GeneratedValue(strategy = IDENTITY)id генерит БД (BIGSERIAL)
@Column(nullable = false, length = 200)NOT NULL VARCHAR(200)
@Enumerated(EnumType.STRING)Enum хранится как строка, а не число
@TransientПоле НЕ сохраняется в БД
Всегда используй @Enumerated(EnumType.STRING). По умолчанию enum хранится как число (порядковый номер). Добавили новый статус в начало — данные в БД сломались. С STRING порядок в enum не важен.

Требования JPA к entity

  1. Класс не final (Hibernate создаёт прокси-подклассы)
  2. Пустой конструктор обязателен — Hibernate использует его при чтении из БД
  3. @Id обязательно
  4. Поля private, доступ через геттеры/сеттеры
  5. Не record — record final, не подходит

JpaRepository

public interface EventRepository extends JpaRepository<Event, Long> {
    // и всё! Spring Data сгенерит реализацию на старте

Что даёт бесплатно: save, findById, findAll, deleteById, existsById, count, deleteAll — и ещё ~20 методов.

save(): INSERT или UPDATE?

Hibernate смотрит на состояние объекта (метод isNew()):

  • id == null → новый → persist() → INSERT
  • id != null → существующий → merge() → UPDATE (или INSERT)
Внимание: никаких SELECT в БД save() не делает! Решение — по состоянию Java-объекта.

Persistence Context и Dirty Checking

Persistence Context — «кэш первого уровня» Hibernate. Живёт в рамках транзакции.

Что даёт:

  • findById дважды в одной транзакции → один SELECT (второй из кэша)
  • Изменения managed-сущности → автоматический UPDATE при коммите
  • Все видят одно и то же состояние

Dirty Checking — Hibernate отслеживает изменения managed-сущностей и генерит UPDATE при завершении транзакции. Поэтому save() при update не обязателен внутри @Transactional.

@Transactional

Spring управляет транзакциями декларативно:

@Service
@Transactional
public class EventService { ... }

Что происходит:

  1. Spring создаёт прокси вокруг сервиса
  2. На входе метода: transactionManager.begin()
  3. Вызов реального метода
  4. Успех → commit() (все изменения + dirty checking → БД)
  5. RuntimeException → rollback()

Правила:

  • @Transactional — на сервисе, не на контроллере
  • readOnly = true — для find* методов (быстрее, без dirty checking)
  • Не работает через self-invocation (вызов изнутри класса)
  • По умолчанию rollback только на RuntimeException
  • Работает только на public методах

Пагинация: Pageable + Page<T>

Зачем: если в БД 1M строк, без пагинации findAll() вытянет всё в память → OOM.

ИнтерфейсРоль
PageableВходной параметр: page, size, sort
Page<T>Результат: content, totalElements, totalPages, number, first, last

Spring Boot автоматически парсит ?page=0&size=20&sort=date,desc в Pageable.

SQL от Hibernate при пагинации — ДВА запроса:

SELECT ... FROM events ORDER BY date DESC LIMIT 20 OFFSET 0;
SELECT count(*) FROM events;

Первый — данные страницы. Второй — count для totalElements и totalPages.

Шаг 6. Repository → JPA

@Repository

}

Всё. Реализацию Spring Data сгенерит сам. Методы save, findById, findAll, deleteById, existsById — те же имена, что были в Map-версии. Сервис и контроллер не меняются.

Шаг 7. EventService с @Transactional

@Service
@Transactional
public class EventService {

    private final EventRepository eventRepository;

    public EventService(EventRepository eventRepository) { this.eventRepository = eventRepository; }

    public EventResponse create(CreateEventRequest request) {
        Event event = new Event(null, request.name(), request.date(),
                                request.venue(), Status.AVAILABLE);
        return EventResponse.from(eventRepository.save(event));
    }

    @Transactional(readOnly = true)
    public EventResponse findById(Long id) {
        Event event = eventRepository.findById(id)
                .orElseThrow(() -> new EventNotFoundException(id));
        return EventResponse.from(event);
    }

    @Transactional(readOnly = true)
    public Page<EventResponse> findAll(Pageable pageable) {
        return eventRepository.findAll(pageable).map(EventResponse::from);
    }

    public EventResponse update(Long id, UpdateEventRequest request) {
        Event event = eventRepository.findById(id)
                .orElseThrow(() -> new EventNotFoundException(id));
        event.setName(request.name());
        event.setDate(request.date());
        event.setVenue(request.venue());
        event.setStatus(request.status());
        return EventResponse.from(event);   // save() НЕ нужен — dirty checking
    }

    public void delete(Long id) {
        if (!eventRepository.existsById(id)) throw new EventNotFoundException(id);
        eventRepository.deleteById(id);
    }
}

🐞 Частые ошибки на практике

1. Забыл пустой конструктор в @Entity
@Entity
public class Event {
    private Long id;
    // конструктор только со всеми полями
    public Event(Long id, String name, ...) { ... }
}
Hibernate при чтении из БД вызывает пустой конструктор, потом заполняет поля через рефлексию. Без него — InstantiationException или NoSuchMethodException.
2. Enum без @Enumerated(STRING) — данные сломались
По умолчанию @Enumerated использует ORDINAL — хранит число (AVAILABLE = 0). Добавил новый статус в начало enum — старые данные стали означать другое. Решение: всегда @Enumerated(EnumType.STRING).
3. save() не возвращает привязанный объект
Event event = new Event(...);
eventRepository.save(event);   // ❌ вернул managed, но result отброшен
return EventResponse.from(event);  // event может быть transient
Решение: Event saved = eventRepository.save(event); return EventResponse.from(saved);. Возвращённый объект — managed, привязан к persistence context.
4. Убрали save() в update, но транзакции нет
@Service
public class EventService {  // ❌ @Transactional нет
    public EventResponse update(Long id, UpdateEventRequest req) {
        Event event = eventRepository.findById(id).orElseThrow(...);
        event.setName(req.name());
        return EventResponse.from(event);   // изменения НЕ сохранятся
    }
}
Без @Transactional нет persistence context — нет dirty checking. Изменения в памяти, БД не тронута. Решение: либо @Transactional на сервисе, либо явный save().
5. Пагинация без sort — нестабильный порядок
GET /api/v1/events?page=0&size=20   // без sort
PostgreSQL не гарантирует порядок без ORDER BY. Одна и та же страница на разных запросах может вернуть разные данные — клиент пропустит или задублирует записи. Решение: всегда указывай sort по уникальному полю (лучше — по id).
6. Два findById ожидают один SQL, но получают два
Причина — вызовы в разных транзакциях или без @Transactional. Persistence context живёт в рамках транзакции. Решение: оборачивай методы сервиса в @Transactional.
7. ddl-auto: update на проде
update никогда не удаляет колонки, не обрабатывает переименования, может генерировать странные ALTER'ы. На проде — опасно. Решение: использовать Liquibase (Спринт 4) + ddl-auto: validate.
8. docker compose down -v «случайно»
-v удаляет volume — все данные БД пропадут. На проде это катастрофа. Решение: используй down без -v. -v — только когда сознательно хочешь «сбросить» БД.
9. Hibernate SQL без значений параметров
select e1_0.id, e1_0.name from events e1_0 where e1_0.id=?
Видно ?, а не значение. Решение: добавить в application.yml: 
logging.level.org.hibernate.type.descriptor.sql.BasicBinder: trace
Тогда в логах будут реальные значения рядом с ?.
10. findAll() вместо findAll(Pageable) на больших таблицах
List<Event> all = eventRepository.findAll();   // ❌ вытянет ВСЮ таблицу в память
На 1M строк — OutOfMemoryError или долгий ответ. Решение: всегда findAll(Pageable) для API-списков.

❓ Вопросы на собеседование

1. Чем JPA отличается от Hibernate?

JPA — спецификация (стандарт Jakarta EE): набор интерфейсов и аннотаций (@Entity, @Id). Hibernate — реализация JPA: конкретный код, который генерит SQL. Можно заменить Hibernate на EclipseLink, OpenJPA — код не изменится. Spring Data JPA — надстройка над JPA: даёт JpaRepository с готовыми методами. В стеке: Spring Data JPA → JPA → Hibernate → PostgreSQL.

2. Что такое persistence context и dirty checking?

Persistence context — «кэш первого уровня» Hibernate в рамках транзакции. Все сущности, загруженные или сохранённые, становятся managed. Dirty checking — механизм: Hibernate сравнивает текущее состояние managed-сущностей с их снимком при загрузке. Если есть изменения — автоматически генерит UPDATE при коммите транзакции. Благодаря этому save() при update внутри @Transactional не обязателен.

3. Как save() определяет INSERT или UPDATE?

Через entityInformation.isNew(entity). По умолчанию — проверка id == null. Если id null → persist() → INSERT, если не null → merge() → UPDATE (или INSERT, если строки нет). В БД save() не смотрит! Только на состояние Java-объекта. Можно переопределить через Persistable или @Version.

4. Что такое @Transactional и где его ставить?

@Transactional — декларативное управление транзакциями. Spring создаёт прокси вокруг сервиса, оборачивает метод в BEGIN / COMMIT / ROLLBACK. Ставить — на сервисе, не на контроллере (HTTP не должен знать о БД) и не на репозитории (Spring Data уже ставит). Для find* — @Transactional(readOnly = true). Не работает при self-invocation (вызов изнутри того же класса) и на не-public методах. По умолчанию rollback только на RuntimeException.

5. Почему @Enumerated(EnumType.STRING) лучше ORDINAL?

ORDINAL хранит порядковый номер enum (0, 1, 2). Проблема: добавили новый статус в начало enum — сдвинулись все числа, старые данные стали означать другое. Например, AVAILABLE был 0, стал 1. Данные в БД сломались. STRING хранит имя ("AVAILABLE") — порядок в enum не важен. Минус: чуть больше места в БД. Всегда используй STRING.

6. Зачем пагинация и как она работает в Spring Data?

Пагинация — разбиение результата на страницы, чтобы не вытянуть миллион строк в память. В Spring Data: Pageable (вход: page, size, sort) → Page<T> (выход: content + метаданные). Spring Boot автоматически парсит ?page=0&size=20&sort=date,desc. Под капотом — два SQL: LIMIT/OFFSET для данных и count(*) для totalElements. Без count используй Slice<T> — быстрее на больших таблицах.

7. Почему после смены Map на PostgreSQL не менялся сервис?

Потому что слоистая архитектура изолирует слои. EventRepository — это абстракция: у неё есть методы save, findById, findAll, deleteById. JpaRepository даёт те же имена. Сервис не знает, где данные — в Map или в БД. Заменили только реализацию (2 класса). Контроллер, DTO, обработчик ошибок — не тронуты. Это главный аргумент за слоистую архитектуру.

8. Что произойдёт, если из метода с @Transactional вылетит RuntimeException?

Spring сделает rollback — все изменения в БД, сделанные в этой транзакции, откатятся. По умолчанию — только для RuntimeException и его наследников. Checked-исключения (IOException, SQLException) — не откатывают. Если нужно — укажи @Transactional(rollbackFor = Exception.class). Это важное различие: Spring считает checked-ошибки «ожидаемыми», а RuntimeException — «багом».
