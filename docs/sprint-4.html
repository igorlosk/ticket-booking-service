📚 Теория

Проблемы ddl-auto: update

Hibernate управляет схемой по модели. Это удобно в разработке, но опасно в продакшене:

СценарийЧто делает HibernateПроблема
Добавили String description как NOT NULLALTER TABLE ADD COLUMN ... NOT NULLУпадёт, если есть строки — нечем заполнить
Переименовали venue → locationADD COLUMN location (не переименует)Данные в venue потеряются
Удалили полеНичегоМусорные колонки копятся
Нет истории изменений—Нельзя понять, что и когда менялось
Нет отката—Откатить деплой нельзя
Правило: ddl-auto: update — только для прототипов. В продакшене — Liquibase (или Flyway) + ddl-auto: validate.

Что такое Liquibase

Liquibase — инструмент контроля версий схемы БД. Идея:

Схема БД — это код. Он должен быть в репозитории, версионироваться, проходить ревью и применяться контролируемо.

Аналогия: Git — для кода, Liquibase — для схемы БД.

Структура проекта с Liquibase

src/main/resources/db/changelog/
├── db.changelog-master.xml          ← точка входа (список миграций)
└── changes/
    ├── 001-create-events-table.xml
    ├── 002-add-description-to-events.xml
    └── ...

Как это работает

Старт приложения ↓ Liquibase читает db.changelog-master.xml ↓ Смотрит таблицу DATABASECHANGELOG: что уже применено ↓ Применяет ТОЛЬКО новые changeset'ы ↓ Записывает их в DATABASECHANGELOG ↓ Hibernate validate: сверяет схему с @Entity ↓ Если совпадает → приложение стартует Если нет → падает с SchemaManagementException

Changeset — единица миграции

<changeSet id="001-create-events-table" author="igor">
    <createTable tableName="events">
        ...
    </createTable>
</changeSet>

Ключевые правила:

  • id + author = уникальный идентификатор
  • Иммутабельность: применил changeset — не меняешь его никогда
  • Нужно изменить — создай новый changeset
  • Liquibase хранит checksum — если изменишь применённый, упадёт с ошибкой

Форматы описания миграций

ФорматПлюсыМинусы
XMLСтандарт индустрии, кросс-БД, много примеровМногословно
YAMLКомпактнееМеньше примеров
JSONКомпактноРедко используется
SQLПрямой SQL, знакомоПривязка к диалекту БД

Используем XML — работает одинаково на PostgreSQL, MySQL, Oracle.

ddl-auto: validate — защита от рассинхрона

Что значит validate: Hibernate при старте сверяет Java-модель со схемой БД. Если что-то не совпадает — падает.

ЗначениеПоведениеКогда использовать
noneНичего не делаетПрод + миграции
validateПроверяет схему с @EntityПрод
updateДобавляет колонки/таблицыТолько прототипы
createУдаляет и создаёт зановоТесты

Служебные таблицы Liquibase

ТаблицаНазначение
databasechangelogИстория применённых миграций (id, author, filename, dateexecuted, checksum)
databasechangeloglockБлокировки — чтобы два инстанса не накатили одно и то же одновременно

Правильный порядок деплоя

1. Пишем миграцию (002-add-description.xml) 2. Добавляем её в master changelog 3. Коммитим в Git 4. Деплоим на сервер 5. Liquibase ПРИМЕНЯЕТ миграцию при старте 6. Hibernate VALIDATE проверяет схему 7. Приложение работает

Гарантия: приложение не запустится, если код ожидает колонку, которой нет в БД.

💻 Пошаговая инструкция

Шаг 1. Зависимость в pom.xml

<dependency>
    <groupId>org.liquibase</groupId>
    <artifactId>liquibase-core</artifactId>
</dependency>

Версию не указываем — Spring Boot parent сам подберёт совместимую.

Шаг 2. Обновить application.yml

spring:
  jpa:
    hibernate:
      ddl-auto: validate        # ← ИЗМЕНИЛИ: update → validate

  liquibase:
    enabled: true
    change-log: classpath:db/changelog/db.changelog-master.xml

logging:
  level:
    liquibase: info

Шаг 3. Очистить БД (для учебного проекта)

docker compose down -v    # -v удаляет volume (все данные!)
docker compose up -d

Потому что таблица events уже создана Hibernate. Если Liquibase попробует её создать — relation "events" already exists.

Шаг 4. Создать master changelog

Файл: src/main/resources/db/changelog/db.changelog-master.xml

<?xml version="1.0" encoding="UTF-8"?>
<databaseChangeLog
        xmlns="http://www.liquibase.org/xml/ns/dbchangelog"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:schemaLocation="http://www.liquibase.org/xml/ns/dbchangelog
                            http://www.liquibase.org/xml/ns/dbchangelog/dbchangelog-4.20.xsd">

    <include file="db/changelog/changes/001-create-events-table.xml"
             relativeToChangelogFile="false"/>

</databaseChangeLog>

Шаг 5. Первая миграция — createTable

Файл: src/main/resources/db/changelog/changes/001-create-events-table.xml

<?xml version="1.0" encoding="UTF-8"?>
<databaseChangeLog
        xmlns="http://www.liquibase.org/xml/ns/dbchangelog"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:schemaLocation="http://www.liquibase.org/xml/ns/dbchangelog
                            http://www.liquibase.org/xml/ns/dbchangelog/dbchangelog-4.20.xsd">

    <changeSet id="001-create-events-table" author="igor">

        <createTable tableName="events">
            <column name="id" type="BIGINT" autoIncrement="true">
                <constraints primaryKey="true" nullable="false"/>
            </column>
            <column name="name" type="VARCHAR(200)">
                <constraints nullable="false"/>
            </column>
            <column name="date" type="TIMESTAMP">
                <constraints nullable="false"/>
            </column>
            <column name="venue" type="VARCHAR(300)">
                <constraints nullable="false"/>
            </column>
            <column name="status" type="VARCHAR(20)">
                <constraints nullable="false"/>
            </column>
        </createTable>

    </changeSet>

</databaseChangeLog>

Шаг 8. Добавляем поле description через миграцию

Создаём миграцию 002-add-description-to-events.xml:

<?xml version="1.0" encoding="UTF-8"?>
<databaseChangeLog
        xmlns="http://www.liquibase.org/xml/ns/dbchangelog"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:schemaLocation="http://www.liquibase.org/xml/ns/dbchangelog
                            http://www.liquibase.org/xml/ns/dbchangelog/dbchangelog-4.20.xsd">

    <changeSet id="002-add-description-to-events" author="igor">

        <addColumn tableName="events">
            <column name="description" type="VARCHAR(1000)"/>
        </addColumn>

    </changeSet>

</databaseChangeLog>

Добавляем include в master changelog:

<include file="db/changelog/changes/002-add-description-to-events.xml"
         relativeToChangelogFile="false"/>

Обновляем Java-код:

  • Event.java — добавляем @Column(length = 1000) private String description; + геттер/сеттер
  • CreateEventRequest — добавляем String description
  • UpdateEventRequest — добавляем String description
  • EventResponse — добавляем String description + в from()
  • EventService.create — event.setDescription(request.description())
  • EventService.update — event.setDescription(request.description())

Шаг 9. Запустить и проверить

  • Liquibase применит миграцию 002
  • Hibernate validate пройдёт
  • В databasechangelog — две строки
  • POST с description сохранится и вернётся

🐞 Частые ошибки на практике

1. Изменил применённый changeset
Применил 001-create-events-table, потом «доработал» — добавил колонку в тот же changeset. Liquibase видит несовпадение checksum и падает: 
ValidationFailedException:
  Migration checksum mismatch for changeset ...
Решение: никогда не трогай применённые changesets. Нужно изменение — новый changeset. Для dev можно очистить databasechangelog и БД полностью.
2. Забыл include в master changelog
Создал файл 002-..., но не добавил <include file="..."/> в db.changelog-master.xml. Liquibase его не увидит. Приложение упадёт с missing column. Решение: всегда добавляй include в master.
3. Миграция ПОСЛЕ кода — неправильный порядок
Сначала добавил поле в Event.java, потом миграцию. При старте: Hibernate validate видит поле в модели, но не видит в БД → падает. Решение: сначала миграция (применяется при старте), потом модель в коде — либо оба в одном коммите, но миграция должна примениться до validate.
4. NOT NULL на новую колонку без default
<column name="description" type="VARCHAR(1000)">
    <constraints nullable="false"/>   <!-- ❌ упадёт, если есть строки -->
</column>
Если в таблице уже есть данные, а новая колонка NOT NULL без defaultValue — Liquibase не сможет её заполнить. Решение: 1) сделать колонку nullable, 2) добавить defaultValue, 3) в несколько миграций: добавить nullable → заполнить → сделать NOT NULL.
5. ddl-auto: update забыли поменять на validate
Оставил update — Hibernate будет конкурировать с Liquibase. Может добавлять колонки, которых нет в миграциях. Рассинхрон схемы и миграций. Решение: с Liquibase — только validate.
6. Перепутал путь к файлу миграции
<include file="changes/001-create-events-table.xml"
         relativeToChangelogFile="true"/>   <!-- ❌ путь относительно master -->
Два режима: relativeToChangelogFile="true" — путь относительно master-файла, ="false" — от корня classpath (resources/). Перепутаешь — файл не найдётся. Решение: используй relativeToChangelogFile="false" с полным путём от resources/.
7. Скопировал миграцию, но забыл поменять id
Скопировал 001-create-events-table, переименовал файл, но оставил id="001-create-events-table". Liquibase считает, что это та же миграция, не применяет новую. Решение: id changeset должен быть уникальным. Меняй id при копировании.
8. Пропустил author
<changeSet id="001">   <!-- ❌ author обязателен -->
Liquibase требует id и author. Решение: всегда указывай оба, лучше — привязка к git config user.name.
9. Продакшен-деплой с Liquibase + down -v
Локально привык делать docker compose down -v для сброса. На проде это удалит все данные. Решение: -v только локально. На проде — никогда.
10. Ожидал, что Liquibase сам откатит миграции
Liquibase не откатывает автоматически, если в changeset не описан <rollback>. По умолчанию при rollback — ошибка. Решение: для сложных миграций описывай <rollback> вручную. Для учебного проекта — не критично.

❓ Вопросы на собеседование

1. Почему ddl-auto: update — плохо для продакшена?

Hibernate с update принимает решения о схеме автоматически, без контроля. Проблемы: 1) никогда не удаляет колонки — мусор копится; 2) не понимает переименований — добавляет новую, старую оставляет; 3) NOT NULL без default упадёт на существующих данных; 4) нет истории изменений — нельзя понять, что менялось; 5) нет отката. В продакшене — только Liquibase/Flyway + validate.

2. Что такое Liquibase и зачем он нужен?

Liquibase — инструмент контроля версий схемы БД. Идея: схема — это код, он должен быть в Git, проходить ревью и применяться контролируемо. Liquibase читает changelog-файлы с миграциями, применяет только новые (отслеживает в databasechangelog), обеспечивает версионирование и откат. Аналогия: Git — для кода, Liquibase — для схемы БД.

3. Что такое changeset и какие правила с ним связаны?

Changeset — единица миграции с уникальной парой id + author. Правила: 1) иммутабельность — применённый changeset нельзя менять (иначе checksum mismatch); 2) изменение — только новым changeset; 3) уникальный id — копируя, меняй; 4) при необходимости отката — описывай <rollback> явно. Liquibase хранит все применённые в таблице databasechangelog.

4. Что делает ddl-auto: validate и почему это полезно?

validate заставляет Hibernate при старте сверить Java-модель со схемой БД. Если что-то не совпадает (нет таблицы, нет колонки, не тот тип) — приложение падает. Это защита от рассинхрона: невозможно выкатить код, ожидающий колонку, не применив миграцию. В продакшене — стандарт: validate + миграции через Liquibase.

5. Зачем таблица databasechangelog?

Liquibase ведёт историю применённых миграций: id, author, filename, dateexecuted, checksum. При старте читает её и применяет только новые changeset'ы. Плюс: считает checksum — если применённый changeset изменили, старт упадёт. Ещё есть databasechangeloglock — блокировки, чтобы два инстанса не применили одно и то же одновременно.

6. Как правильно добавить новую колонку в проде?

Порядок: 1) создаём новую миграцию addColumn (не трогая старые); 2) добавляем в master changelog; 3) обновляем Java-модель (@Entity); 4) коммитим в Git; 5) деплоим. При старте Liquibase применит миграцию до того, как Hibernate с validate проверит схему. Если колонка NOT NULL — используй трюк: сначала nullable → заполнить данные → сделать NOT NULL, иначе упадёт на существующих строках.

7. Как откатить миграцию в Liquibase?

Через команду liquibase rollback или в Spring Boot — свойство spring.liquibase.rollback-.... Но автоматического отката нет — нужно явно описать тег <rollback> в changeset. Без него Liquibase не знает, как откатить. Плюс — честно говоря, в реальных проектах откат миграций используется редко: обычно откатывают деплой, а данные остаются. Поэтому для большинства проектов rollback — «на случай».

8. Liquibase или Flyway — что выбрать?

Оба — инструменты миграций. Liquibase: больше форматов (XML, YAML, JSON, SQL), кросс-БД, богаче возможности (контексты, labels, preconditions). Flyway: проще, работает «из коробки» с SQL-файлами, популярнее в небольших проектах. В enterprise чаще Liquibase — из-за гибкости. Оба — стандарт индустрии, выбор часто зависит от команды. В нашем проекте — Liquibase, потому что он лучше подходит для сложных схем.
